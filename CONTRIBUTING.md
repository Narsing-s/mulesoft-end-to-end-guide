# Contributing to MuleJourney

Thank you for your interest in contributing to **MuleJourney**. This project is built to make MuleSoft learning practical, structured, and accessible, and contributions from developers, support engineers, learners, technical writers, testers, and reviewers are welcome.

## 🌟 Why contribute?

You can help improve MuleJourney by:

- Adding accurate MuleSoft explanations
- Expanding DataWeave examples and exercises
- Adding interview questions and scenario-based answers
- Creating hands-on labs
- Improving diagrams and learning paths
- Adding production troubleshooting scenarios
- Fixing broken links or incorrect examples
- Improving accessibility and UI/UX
- Improving documentation and navigation
- Adding automated tests and validation
- Sharing practical integration patterns

You do **not** need to be a MuleSoft expert to contribute. Documentation fixes, beginner-friendly explanations, examples, testing, and issue reports are valuable contributions.

## 🚀 Quick contribution flow

```text
Find an issue or idea
        ↓
Discuss the approach when needed
        ↓
Fork the repository
        ↓
Create a focused branch
        ↓
Make the change
        ↓
Test and verify links/examples
        ↓
Update documentation
        ↓
Open a Pull Request
        ↓
Review → Improve → Merge
```

## 🧭 Good first contributions

If you are new to the project, start with:

- Fixing a typo or unclear explanation
- Improving an example's input/output
- Adding a missing DataWeave example
- Adding a beginner question and answer
- Improving a diagram
- Reporting a broken internal link
- Improving accessibility labels
- Improving page navigation
- Adding a small troubleshooting scenario

Look for issues labeled **good first issue**, **documentation**, **help wanted**, or similar contribution labels when available.

## 📝 Documentation contributions

A strong learning example should explain:

1. What the concept is.
2. Why it is used.
3. When to use it.
4. A realistic example.
5. Input data.
6. Mule/DataWeave/API configuration.
7. Expected output.
8. Common mistakes.
9. Troubleshooting guidance where useful.
10. Related topics.

Prefer clear explanations over unnecessary complexity.

## 🧑‍💻 DataWeave contributions

For DataWeave examples, use a consistent structure whenever practical:

```text
Question / Goal
      ↓
Input
      ↓
DataWeave
      ↓
Output
      ↓
Explanation
      ↓
Alternative / Edge Case
```

Examples should be deterministic, readable, and easy for another learner to reproduce.

## 🧪 Labs and practical scenarios

New labs should preferably include:

- Objective
- Prerequisites
- Scenario
- Requirements
- Starting input/configuration
- Expected result
- Validation steps
- Failure scenario
- Troubleshooting hints
- Solution or reference implementation
- Learning outcome

The project's preferred learning loop is:

**Build → Test → Break → Debug → Fix → Explain**

## 🎨 UI contributions

For portal changes:

- Keep the interface responsive.
- Preserve keyboard accessibility.
- Use meaningful labels and focus states.
- Keep navigation consistent.
- Do not add decorative UI that does not provide value.
- Ensure every new button or link has a working destination/action.
- Avoid breaking the static/offline-friendly learning experience.

## 🔍 Before opening a pull request

Please check:

- [ ] The change solves a specific problem or adds useful learning value.
- [ ] Documentation is clear and grammatically readable.
- [ ] Internal links point to existing files/pages.
- [ ] Code examples are formatted consistently.
- [ ] DataWeave examples include input and output when applicable.
- [ ] UI changes work on desktop and mobile layouts.
- [ ] No passwords, tokens, API keys, private keys, or personal secrets were committed.
- [ ] No unrelated files were changed.
- [ ] The project disclaimer is preserved where applicable.
- [ ] The contribution follows the Code of Conduct.

## 🔐 Security issues

Do not publish credentials, private keys, access tokens, passwords, or other sensitive information in issues or pull requests.

If you discover a security issue, report it privately through the repository's available security/contact mechanism rather than publicly exposing exploit details or credentials.

## 📦 Commit guidance

Use clear commit messages that describe the change, for example:

- `docs: add DataWeave filter examples`
- `docs: improve APIkit troubleshooting guide`
- `fix: correct broken learning path link`
- `feat: add production support lab`
- `test: validate documentation links`

Keep commits focused where practical.

## 🔀 Pull requests

A useful pull request should explain:

### What changed?

Briefly describe the files and learning experience affected.

### Why?

Explain the problem, gap, or learner need being addressed.

### How was it verified?

Mention tests, link checks, manual verification, or example validation performed.

### Screenshots

For meaningful UI changes, include before/after screenshots when useful.

## 💡 Propose ideas before large changes

For large features, new learning systems, major UI redesigns, or substantial content reorganizations, open an issue or discussion first when possible. This helps avoid duplicated work and keeps the project structure coherent.

Small documentation improvements can usually be submitted directly as a pull request.

## 🤝 Review philosophy

Pull-request review is about improving the contribution, not judging the contributor. Reviewers should:

- Explain requested changes clearly.
- Distinguish required fixes from optional suggestions.
- Provide evidence for technical corrections.
- Welcome improvements from contributors.
- Keep feedback respectful and actionable.

## 📣 Help grow the project

If you find MuleJourney useful, you can help the project grow by:

- ⭐ Starring the repository
- 🐛 Reporting useful issues
- 💡 Proposing learning topics
- 🧪 Contributing labs
- 📝 Improving documentation
- 🔀 Opening pull requests
- 📢 Sharing the project with MuleSoft learners and integration engineers
- 👥 Helping beginners understand difficult topics

The goal is not simply to increase repository activity. The goal is to build a useful community-maintained MuleSoft learning resource.
