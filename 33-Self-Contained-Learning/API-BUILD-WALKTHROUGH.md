# Build Your First REST API — Complete Internal Walkthrough

## Goal

Build:

```text
POST /api/customers
GET  /api/customers/{id}
```

The API receives JSON, validates basic fields, transforms data, and returns JSON.

## Mental model

```text
HTTP client
   ↓
Listener
   ↓
Flow
   ↓
Validation / transformation
   ↓
Business logic
   ↓
Response
```

## Example request

```json
{
  "name":"Ravi Kumar",
  "email":"ravi@example.com",
  "mobile":"9999999999"
}
```

## Example response

```json
{
  "message":"Customer created",
  "customer": {
    "name":"Ravi Kumar",
    "email":"ravi@example.com"
  }
}
```

## Simple Mule XML shape

```xml
<flow name="post-customer-flow">
    <http:listener config-ref="HTTP_Listener_config" path="/api/customers" allowedMethods="POST"/>
    <set-variable variableName="customer" value="#[payload]"/>
    <choice>
        <when expression="#[isEmpty(vars.customer.name default '')]">
            <raise-error type="APP:VALIDATION" description="name is required"/>
        </when>
        <otherwise>
            <transform>
                <ee:message>
                    <ee:set-payload><![CDATA[
%dw 2.0
output application/json
---
{
  message: "Customer created",
  customer: {
    name: vars.customer.name,
    email: vars.customer.email
  }
}
                    ]]></ee:set-payload>
                </ee:message>
            </transform>
        </otherwise>
    </choice>
</flow>
```

The exact namespace declarations depend on the Mule project generated by Studio; learners should copy the flow body into a valid project rather than blindly treating the snippet as a complete standalone Mule application.

## What happens at runtime?

1. The listener accepts the HTTP request.
2. Mule creates an event.
3. The request body becomes the payload.
4. The flow stores the input in a variable.
5. Validation checks the required field.
6. DataWeave constructs the response.
7. The HTTP response is returned.

## Failure cases

| Situation | Expected behavior |
|---|---|
| Missing name | validation error |
| Invalid JSON | client/request error |
| Wrong method | method-not-allowed behavior |
| Wrong path | not-found behavior |
| Downstream unavailable | dependency error |
| Unexpected exception | controlled server error |

## Debugging checklist

1. Is the listener running?
2. Is the port correct?
3. Is the path correct?
4. Is the HTTP method correct?
5. Is `Content-Type` correct?
6. What is the payload before transformation?
7. What variables exist?
8. Which processor generated the error?
9. What correlation ID identifies the request?
10. Does the response leak internal details?

## Production upgrade

A real API should add:

- API contract
- input validation
- consistent error model
- authentication and authorization
- structured logs
- correlation ID
- timeouts
- downstream retry rules
- idempotency where needed
- MUnit tests
- environment configuration
- secrets outside source code
- monitoring and alerts
- deployment strategy
- rollback plan
